一、项目定位

项目名称建议：**基于 Gin + GORM 的短视频 Feed 流后端系统**

这是一个参考开源项目后自行实现的类抖音短视频社区后端，核心覆盖账号、视频发布、Feed 浏览、点赞评论关注、基础私信和用户主页聚合。项目适合投递 **Go 后端开发实习 / 校招后端开发**，重点体现 Gin/GORM/MySQL、JWT 鉴权、事务一致性、游标分页和基础 Redis 缓存能力。

建议放在简历的 **核心项目**。原因是模块完整度比普通 CRUD 高，能围绕鉴权、一致性、幂等、分页、缓存展开面试追问。

二、已实现功能梳理

账号注册、登录、JWT 鉴权、登出：

- 核心接口：`POST /account/register`、`POST /account/login`、`GET /account/me`、`POST /account/logout`
- 关键表：`accounts`
- 关键字段：`username` 唯一索引、`password_hash`、`token`、`avatar_url`、`bio`
- 已实现点：bcrypt 密码加密；JWT 生成和解析；JWT 中间件从 `Authorization: Bearer <token>` 取 token；解析后写入 `userID`、`username` 到 Gin Context；登出通过清空数据库 token 并删除 Redis token cache 让旧 token 失效。
- 难点：这个项目不是纯无状态 JWT，而是“JWT + 服务端 token 校验”，所以能主动登出；Redis token cache miss 后会回源数据库。

视频上传、封面上传、视频发布、视频详情：

- 核心接口：`POST /video/uploadVideo`、`POST /video/uploadCover`、`POST /video/publish`、`POST /video/getDetail`
- 关键表：`videos`、`tags`、`video_tags`
- 关键数据：视频文件落到 `.run/uploads/videos/...`，封面落到 `.run/uploads/covers/...`，数据库只存 URL，不存文件本体。
- 已实现点：上传接口和发布接口拆开；视频仅支持 `.mp4`，封面支持 `.jpg/.jpeg/.png/.webp`；发布时从标题和描述提取 `#tag`，统一小写后写入标签表和关联表；发布视频、标签、关联关系在 GORM 事务中完成。
- 难点：本地路径和访问 URL 分离；标签唯一索引处理并发创建；视频详情使用 Redis cache-aside 缓存，TTL 5 分钟。

最新 Feed、标签 Feed、作者作品列表：

- 核心接口：`POST /feed/listLatest`、`POST /feed/listByTag`、`POST /video/listByAuthorID`
- 关键表：`videos`、`tags`、`video_tags`
- 已实现点：按 `created_at DESC, id DESC` 排序；使用 `latest_time + latest_id` 复合游标分页；查询 `limit+1` 条判断 `has_more`。
- 难点：避免 offset 分页在 Feed 数据新增时出现重复或漏数据；用 `created_at + id` 解决同一毫秒创建多条视频时只靠时间游标不稳定的问题。

点赞、取消点赞、点赞列表：

- 核心接口：`POST /like/like`、`POST /like/unlike`、`POST /like/isLiked`、`POST /like/listLikedVideos`
- 关键表：`likes`，以及 `videos.likes_count`
- 已实现点：`likes` 使用 `(video_id, account_id)` 唯一索引；点赞和 `likes_count + 1` 放在同一事务；重复点赞返回幂等成功，不重复加计数；取消点赞不存在时也返回成功，不重复减计数；点赞列表按 `likes.created_at DESC, likes.id DESC` 分页。
- 难点：点赞表没有 `DeletedAt`，避免 GORM 软删除导致唯一索引占用，影响再次点赞；点赞/取消后删除视频详情缓存。

评论发布、删除、评论列表：

- 核心接口：`POST /comment/publish`、`POST /comment/delete`、`POST /comment/listComment`
- 关键表：`comments`，以及 `videos.comments_count`
- 已实现点：评论内容去空格并限制 500 字；发布评论和 `comments_count + 1` 放在同一事务；删除评论和 `comments_count - 1` 放在同一事务；评论列表使用复合游标分页。
- 难点：删除时目前只允许评论作者本人删除；“评论不存在”和“不是本人评论”现在都返回评论不存在，这是可改进点。

关注、取关、粉丝/关注列表：

- 核心接口：`POST /follow/follow`、`POST /follow/unfollow`、`POST /follow/isFollowing`、`POST /follow/listFollower`、`POST /follow/listFollowing`
- 关键表：`follows`
- 已实现点：`(follower_id, vlogger_id)` 唯一索引；禁止关注自己；重复关注视为成功；取关不存在关系也视为成功；粉丝列表和关注列表 join `accounts` 返回用户信息，并按关注时间复合游标分页。
- 难点：区分 `follower_id` 和 `vlogger_id`，否则粉丝列表和关注列表很容易写反。

私信发送、会话列表：

- 核心接口：`POST /message/sendMsg`、`POST /message/listConversation`
- 关键表：`messages`
- 已实现点：禁止给自己发消息；校验接收方存在；内容限制 1000 字；会话查询使用 `(from_id=A AND to_id=B) OR (from_id=B AND to_id=A)` 查询双方消息。
- 难点：目前是基础文本私信，没有已读状态、会话表、WebSocket/SSE 实时推送。

用户主页聚合：

- 核心接口：`POST /account/getProfile`
- 关键数据：`accounts` 用户信息、`videos` 视频数和获赞数、`follows` 粉丝数和关注数。
- 已实现点：聚合返回用户资料、作品数、获赞数、粉丝数、关注数。
- 难点：当前是实时查 MySQL 聚合，没有接入 profile cache。

Redis 已实现部分：

- 已实现：Redis client、key prefix、Ping 检查、`enabled` 配置、token cache、video detail cache。
- token cache 已实现 hit 快速路径、miss/异常/mismatch 回源 MySQL 和回填，TTL 不超过 JWT 剩余有效期和 5 分钟。
- video detail cache：`myfeed:video:detail:{videoID}`，TTL 5 分钟；详情 cache-aside；点赞/评论变更后删除详情缓存。
- 未实现：Feed 缓存、Profile 缓存、热榜 ZSET、限流、缓存击穿保护等。

当前仍需收口：

- token cache 折中改造已落地，可以在简历和面试中说明短 TTL、mismatch 回源和 Redis 故障降级，但要同时说明异常时有最长 5 分钟的旧值窗口。
- `doc/05` 删除评论示例写了 `content_id`，代码实际需要 `comment_id`。
- 评论列表代码没有校验视频是否存在，不存在时倾向返回空列表；文档里写了可能 404，需要统一。
- `ProfileKey`、`FeedLatestKey` 只是 key 预留，profile/feed 业务缓存没有接入。

四、推荐写进简历的技术亮点

1. 分层架构

- 简历写法：采用 handler/service/repository 分层组织 Gin 项目，拆分账号、视频、Feed、互动、社交等业务模块。
- 面试讲法：handler 只做参数绑定和响应，service 放业务规则，repository 只负责 DB 操作，后面加缓存和测试更容易。
- 追问：为什么不直接在 handler 里写 SQL？
- 回答要点：小项目可以写，但复杂后会难测、难复用、难维护；分层能让业务规则和 HTTP 细节分开。

2. JWT 鉴权与登出失效

> 下面关于 5 分钟 TTL 和 mismatch 回源的话术已有代码和测试支撑，可以用于简历或面试。

- 简历写法：实现 JWT 鉴权中间件，结合数据库 token 和 Redis token cache 支持服务端登出失效。
- 面试讲法：JWT 本身签发后很难主动失效，所以我在账号表保存当前有效 token，鉴权时解析 JWT 后还要比对服务端 token。
- 追问：Redis 和数据库谁是最终可信来源？
- 回答要点：MySQL 是最终可信来源，Redis 只是加速；Redis miss 或异常时回源 MySQL。
- 一致性边界：正常登出会主动删除缓存；Redis 删除失败时接受最长 5 分钟旧值窗口，不宣称生产级严格实时撤销。

3. bcrypt 密码加密

- 简历写法：使用 bcrypt 对用户密码进行哈希存储，避免明文密码入库。
- 面试讲法：注册时生成 hash，登录时用 `CompareHashAndPassword` 比对，不需要也不应该还原原密码。
- 追问：为什么不用 MD5？
- 回答要点：MD5 太快，容易被撞库；bcrypt 自带 cost，适合密码存储。

4. GORM 事务保证一致性

- 简历写法：使用 GORM 事务保证视频发布、点赞计数、评论计数等多表写入一致性。
- 面试讲法：点赞不是只插一条 like，还要更新 `videos.likes_count`，这两个动作必须一起成功或一起失败。
- 追问：事务里更新计数为什么用 `likes_count + 1`？
- 回答要点：用数据库原子表达式避免先查再写导致并发覆盖。

5. 唯一索引 + 幂等设计

- 简历写法：通过唯一索引和业务幂等逻辑处理重复点赞、重复关注等请求。
- 面试讲法：`likes` 表限制同一个用户对同一个视频只能有一条记录；重复点赞触发唯一冲突时返回成功但不重复加计数。
- 追问：为什么还要查重，唯一索引不够吗？
- 回答要点：唯一索引是最终兜底，service 层负责把数据库冲突转成业务语义。

6. 复合游标分页

- 简历写法：列表接口采用 `created_at + id` 复合游标分页，避免 offset 在动态 Feed 场景下重复或漏数据。
- 面试讲法：只用 `created_at` 会遇到同一时间多条数据的问题，所以用 `created_at DESC, id DESC` 排序，并用双条件翻页。
- 追问：为什么不用 offset？
- 回答要点：Feed 数据不断新增，offset 容易重复/漏；页数越深扫描成本越高。

7. DTO 隔离数据库模型

- 简历写法：使用 DTO 隔离数据库模型和接口返回，统一毫秒时间戳输出。
- 面试讲法：GORM Model 里有 `DeletedAt/UpdatedAt/PasswordHash/Token` 等不该暴露的字段，所以返回 DTO 更安全。
- 追问：DTO 会不会很麻烦？
- 回答要点：有一点转换成本，但换来接口稳定和字段安全。

8. Redis cache-aside 缓存

- 简历写法：实现 Redis cache-aside 缓存视频详情和 token，支持缓存 miss 回源 MySQL。
- 面试讲法：详情接口先读 Redis，miss 后读 MySQL 并写回；点赞/评论会影响详情里的计数，所以写操作后删除详情缓存。
- 追问：缓存和数据库短暂不一致怎么办？
- 回答要点：当前用删除缓存降低脏读窗口；后续可加延迟双删、互斥锁或热点保护。

六、项目面试问题清单

1. 项目整体设计

- Q：这个项目主要解决什么问题？  
  A：它是一个短视频社区后端 MVP，核心是用户能发视频、刷 Feed、互动和查看主页。我重点练的是 Go 后端工程结构、数据一致性和 Feed 分页。
- Q：为什么用单体架构？  
  A：现阶段功能还在学习和验证阶段，单体更适合把事务和业务边界写清楚。微服务会增加调用链和数据一致性复杂度。
- Q：模块怎么拆的？  
  A：按业务域拆成 account、video、feed、like、comment、follow、message、profile，再用 router 做依赖装配。
- Q：项目里最有技术含量的点是什么？  
  A：我觉得是互动计数一致性、点赞关注幂等、JWT 主动失效、复合游标分页和 Redis cache-aside。
- Q：参考开源项目，你自己做了什么？  
  A：我参考的是方向和功能拆分，实际实现时按自己的阶段做了取舍，比如先做单体同步版本，不把 MQ、SSE、微服务写成完成。

2. Gin / GORM / MySQL

- Q：Gin 里 handler 做什么？  
  A：主要做参数绑定、拿上下文用户 ID、调用 service、根据错误返回状态码。
- Q：GORM 事务怎么用？  
  A：我在 repository 封装 `Transaction`，传入事务版 repo，service 把多步写操作放进去。
- Q：AutoMigrate 做了什么？  
  A：启动时自动迁移 accounts、videos、tags、video_tags、likes、comments、follows、messages 等表。
- Q：你怎么处理数据库唯一冲突？  
  A：封装了 MySQL 1062 判断，把重复用户名、重复点赞、重复关注转换成业务错误或幂等成功。
- Q：为什么冗余 `likes_count/comments_count`？  
  A：详情和列表高频展示计数，实时 count 明细表成本高，所以写入时维护冗余字段。

3. JWT 鉴权与登出失效

- Q：JWT 里放了什么？  
  A：放 account_id、username、签发时间和过期时间。
- Q：怎么防止伪造 token？  
  A：使用 HS256 签名，解析时检查签名算法和 secret。
- Q：登出怎么让 token 失效？  
  A：数据库里保存当前有效 token，登出时清空数据库 token 并删除 Redis token cache。
- Q：Redis token cache 挂了怎么办？  
  A：鉴权会回源 MySQL；登录和登出也以 MySQL 结果为准。Redis 是加速层，写失败只会留下最长 5 分钟的旧缓存窗口。
- Q：JWT_SECRET 不配置会怎样？  
  A：代码会生成随机 secret，重启后旧 token 全失效，适合开发提醒，正式环境必须配置稳定 secret。

4. Feed 流分页设计

- Q：为什么不用 offset？  
  A：Feed 数据会不断新增，offset 翻页容易重复或漏数据，深分页性能也差。
- Q：为什么需要 `latest_time + latest_id`？  
  A：只用时间遇到同一毫秒多条数据会不稳定，加上 id 可以保证严格顺序。
- Q：SQL 条件怎么写？  
  A：排序是 `created_at DESC, id DESC`，下一页条件是 `created_at < t OR (created_at = t AND id < id)`。
- Q：`has_more` 怎么判断？  
  A：多查一条，也就是 `limit+1`，如果查到多的一条说明还有下一页。
- Q：哪些接口用了这种分页？  
  A：最新 Feed、标签 Feed、作者作品、点赞列表、评论列表、粉丝/关注列表、私信会话列表。

5. 点赞、评论、关注的一致性与幂等

- Q：重复点赞怎么办？  
  A：唯一索引兜底，重复插入时返回当前点赞数，不重复加计数。
- Q：取消点赞重复请求怎么办？  
  A：删除不到记录就认为已经是目标状态，返回成功，不重复减计数。
- Q：点赞计数如何保证一致？  
  A：创建 like 和更新 `likes_count` 在同一个事务里。
- Q：评论删除有什么权限？  
  A：当前只允许评论作者删除自己的评论，还没有做视频作者管理评论。
- Q：关注为什么也需要唯一索引？  
  A：防止同一个用户重复关注同一个博主，尤其是并发请求下 service 查重不够可靠。

6. Redis 缓存设计

- Q：项目里 Redis 用在哪？  
  A：token cache 和 video detail cache。
- Q：视频详情缓存流程？  
  A：先查 Redis，miss 查 MySQL，再写 Redis；点赞评论后删除详情缓存。
- Q：token cache 流程？  
  A：鉴权先查 Redis，token 相同直接通过；miss、异常或 mismatch 时查数据库，数据库匹配后用不超过 5 分钟的 TTL 回填。
- Q：Redis 不可用会不会影响核心业务？  
  A：启动时 Ping 失败会关闭缓存；运行时缓存失败通常回源 MySQL。
- Q：为什么没缓存 Feed？  
  A：Feed 缓存会涉及 ZSET 顺序、分页语义和脏数据清理，我计划在有压测基线后再补。

7. 缓存穿透、击穿、一致性问题

- Q：你现在处理缓存穿透了吗？  
  A：视频详情没有做空值缓存，所以严格说还没完整处理穿透。
- Q：热点 key 击穿怎么办？  
  A：后续可以加互斥锁、singleflight 或短 TTL 空值缓存。
- Q：缓存一致性怎么保证？  
  A：视频详情是写 MySQL 成功后删除缓存；token 登录后 SET、登出后 DEL，并用最长 5 分钟 TTL 约束异常旧值窗口。
- Q：删除缓存失败怎么办？  
  A：记录日志且不回滚 MySQL；详情依赖自身 TTL，token 旧值最多保留 5 分钟。当前个人项目接受有界最终一致性。
- Q：为什么不直接更新缓存？  
  A：详情 DTO 由多个字段组成，删除缓存更简单，下一次按数据库重建，学习阶段更稳。

8. 数据库索引与事务

- Q：视频表有哪些索引？  
  A：作者 + 创建时间索引、创建时间索引，用于作者作品和最新 Feed。
- Q：likes 表为什么没有软删除？  
  A：软删除会让唯一索引仍占用，取消点赞后再次点赞可能冲突。
- Q：评论为什么可以软删除？  
  A：评论需要保留删除状态和审计空间，列表默认会过滤软删除。
- Q：哪些地方用了事务？  
  A：视频发布写标签、点赞更新计数、评论更新计数。
- Q：还有哪些事务短板？  
  A：关注目前没有计数字段，所以没事务；后续如果做粉丝数冗余，就要把关系写入和计数更新放一起。

9. Go 语言基础

- Q：context 在项目里怎么用？  
  A：Redis 操作用 context 加 50ms 超时，避免缓存请求拖住主链路。
- Q：错误处理怎么做？  
  A：service 定义业务错误，handler 用 `errors.Is` 映射 HTTP 状态码。
- Q：接口用在哪里？  
  A：token cache 和 detail cache 用接口隔离，业务层不直接依赖 go-redis。
- Q：包结构为什么放 internal？  
  A：`internal` 下的包只给本项目使用，符合 Go 的封装习惯。
- Q：Go 里怎么避免密码泄露到 JSON？  
  A：`PasswordHash`、`Token` 字段用了 `json:"-"`，接口返回也用 DTO 控制字段。

10. 测试、联调和项目短板

- Q：你做了哪些测试？  
  A：有 service 参数校验测试、httptest 路由测试、MySQL 集成测试框架和点赞幂等测试。
- Q：当前测试是否充分？  
  A：不充分，主要覆盖关键边界，MySQL 集成测试默认 skip，还需要补更多事务和分页测试。
- Q：你实际跑过测试吗？  
  A：我跑了 `go test ./...`，默认测试通过；需要真实 MySQL 的用例要设置 `RUN_MYSQL_TESTS=1`。
- Q：项目最大短板是什么？  
  A：缺少完整压测、缓存击穿保护、统一错误响应和更完整的集成测试。
- Q：如果继续优化你先做什么？  
  A：先补测试和文档一致性，再做 Feed/详情接口压测，最后按数据决定 Redis Feed 缓存和限流。

七、60 秒和 3 分钟项目介绍

60 秒版本：

我做的是一个用 Go 实现的短视频 Feed 流后端系统，整体是 Gin + GORM + MySQL 的单体架构。功能上覆盖了账号注册登录、JWT 鉴权、视频上传发布、最新 Feed、标签 Feed、点赞评论关注、基础私信和用户主页。

这个项目我重点不是包装成高并发大系统，而是把后端基础能力做扎实，比如 handler/service/repository 分层、bcrypt 密码加密、JWT 登出失效、GORM 事务、点赞关注幂等、`created_at + id` 复合游标分页。现在 Redis 已经接入了 token cache 和视频详情 cache，但 RabbitMQ、SSE、分片上传、推荐算法这些还只是后续规划，我不会写成已完成。

3 分钟版本：

我这个项目是一个类抖音的短视频 Feed 流后端，主要用 Go、Gin、GORM、MySQL 实现，后来接入了 Redis 做部分缓存。项目最开始是参考开源项目的功能方向，但我没有直接照搬完整架构，而是按本科生能真正讲清楚的阶段来做：先完成单体同步 MySQL 版本，再补缓存和测试。

功能上，账号模块支持注册、登录、JWT 鉴权、登出和当前用户信息。密码用 bcrypt 存 hash，JWT 中间件会解析 token，并且和服务端当前 token 比对，所以可以支持主动登出。Redis 接入后，token 校验会先查 Redis，miss、读取异常或 mismatch 时回源 MySQL。

视频模块支持视频和封面上传，文件落本地目录，数据库只保存可访问 URL。发布视频时会写 videos 表，同时从标题和描述里提取 `#tag`，写 tags 和 video_tags，这几个写操作放在一个 GORM 事务里。Feed 模块支持最新流、标签流和作者作品列表，分页没有用 offset，而是使用 `created_at + id` 复合游标，避免 Feed 数据新增时翻页重复或漏数据。

互动模块包括点赞、评论、关注。点赞表有用户和视频的唯一索引，重复点赞会被当作幂等成功，不会重复增加 `likes_count`。评论发布和删除会维护 `comments_count`。关注也用了唯一索引，避免重复关注。私信目前是基础的一对一文本消息，支持发送和会话分页查询，没有做实时推送。

目前我认为项目能体现 Go 后端的工程基本功，比如分层、事务、索引、幂等、分页和缓存降级。但我也知道它还不是生产级系统，像 RabbitMQ、Worker、SSE、分片上传、推荐算法、完整压测和高可用部署还没有实现。后续我会优先补充 MySQL 集成测试、接口压测、慢 SQL 分析，再继续做 Feed Redis 缓存和限流。

八、面试官深挖时的答题策略

应该主动讲：

- 为什么项目选择单体，而不是一开始微服务。
- JWT 主动失效为什么需要服务端 token 校验。
- 点赞/关注为什么要唯一索引和幂等。
- Feed 为什么不用 offset，而用复合游标。
- Redis 只是缓存层，MySQL 是主存储。
- 哪些功能已实现，哪些只是规划。

不要主动提：

- RabbitMQ、SSE、微服务、推荐算法，除非面试官问后续规划。
- “高并发”“高可用”“生产级”这类没有证据支撑的词。
- 没有真实数据的 QPS、p95、p99。
- 复杂推荐算法，因为当前只是最新流和标签流。

被问到未实现功能时：

可以说：“这个我还没实现，所以简历里不会写成已完成。我现在的优先级是先保证同步 MySQL 版本的正确性，比如事务、幂等、分页和测试。后续如果做异步化，我会从点赞事件入手，用 MQ + Worker，并且要处理重复消费和最终一致性。”

如何讲“参考开源项目”：

不要说“照着开源项目做的”。可以说：“我参考了开源项目的业务方向和模块划分，但实现时做了取舍，没有直接上完整中间件栈，而是先自己实现单体版本，把账号、视频、Feed、互动这些核心链路跑通，再逐步引入 Redis。”

如何体现不是只会 CRUD：

重点讲这些：

- 为什么要事务。
- 为什么要唯一索引。
- 为什么要幂等。
- 为什么 Feed 不适合 offset。
- 为什么 DTO 不直接暴露 Model。
- 为什么 Redis 要能降级。
- 为什么不能没有压测就宣称性能优化。

九、项目补强建议

简历前必须补：

1. 修正文档和代码不一致  
   为什么：面试官看 README 和代码冲突会减分。  
   怎么补：统一 `latest_time + latest_id`、DTO 字段、评论删除参数、Redis 已实现范围。  
   升级描述：项目文档与接口实现保持一致，沉淀 API 文档和模块说明。

2. 修复负数游标 handler 少 `return` 的小问题  
   为什么：`feed`、`video` 部分 handler 返回 400 后还会继续执行。  
   怎么补：检测 `latest_time < 0` 后立刻 `return`。  
   升级描述：完善参数校验和错误返回，减少异常请求进入业务层。

3. 补一组真实 MySQL 集成测试  
   为什么：事务、唯一索引、分页必须靠真实数据库验证。  
   怎么补：设置 `RUN_MYSQL_TESTS=1`，补点赞并发、评论计数、复合游标同时间戳测试。  
   升级描述：通过集成测试验证点赞幂等、计数一致性和游标分页稳定性。

面试前最好补：

1. 做一次 Bruno/curl 完整链路演示  
   为什么：面试时能讲清楚接口如何串起来。  
   怎么补：注册、登录、上传、发布、Feed、点赞、评论、关注、主页全链路。  
   升级描述：完成短视频社区核心业务闭环联调。

2. 对 Feed 和详情接口做基础压测  
   为什么：没有数据就不要说性能优化。  
   怎么补：用 hey/wrk 记录 MySQL-only 和 Redis detail cache 的响应差异。  
   升级描述：建立接口性能基线，具备 Redis 优化前后对比能力。

3. 补 EXPLAIN 截图或记录  
   为什么：能证明你理解索引，不只是写了 tag。  
   怎么补：对最新 Feed、作者作品、点赞列表、评论列表查询做 EXPLAIN。  
   升级描述：结合查询模式设计复合索引并验证执行计划。

有时间再补：

1. Feed Redis ZSET 缓存  
   为什么：首页 Feed 是高频读。  
   怎么补：先只缓存第一页视频 ID，详情仍复用 video detail cache。

   为什么：登录、上传、评论、私信都容易被刷。

   为什么：适合后续削峰和异步处理。

   怎么补：增加 MIME sniff、孤儿文件清理、后续再考虑 OSS/分片上传。  
   升级描述：完善上传安全校验和文件生命周期管理。

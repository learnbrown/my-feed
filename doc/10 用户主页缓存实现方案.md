# 用户主页缓存轻量实现方案

> 状态：已实现并验收（2026-08-25）  
> 适用阶段：V1.0 Redis 高并发读优化  
> 设计原则：与当前个人本地开发项目的复杂度保持一致，不按生产上线系统扩张

## 1. 为什么现在缓存用户主页

当前 `ProfileService.GetProfile(accountID)` 为一次主页请求依次聚合：

1. 账号基本信息。
2. 正常状态的视频数。
3. 作者所有视频的获赞总数。
4. 粉丝数。
5. 关注数。

也就是说，一次 `/account/getProfile` 会触发 5 次 MySQL 查询。主页又属于重复访问明显、允许短暂旧数据的读接口，因此适合作为视频详情之后的第二个 Cache Aside 练习。

这次改造只优化内部读路径，不改变 HTTP 路由、请求字段、成功响应 JSON 或错误状态码。

## 2. 本轮目标与非目标

### 2.1 目标

- 缓存现有 `Profile` DTO，减少重复聚合查询。
- 固定使用 60 秒 TTL。
- Redis miss 或异常时回源 MySQL。
- 关注、点赞和发布等明确影响主页统计的写操作成功后主动删除缓存。
- Redis 读、写、删除失败只记录异常日志，不改变 MySQL 业务结果。
- 用单元测试、miniredis 测试和现有 MySQL 集成测试验证主要边界。

### 2.2 本轮不做

- 不做缓存预热。
- 不缓存不存在的账号，不做空值缓存。
- 不做 singleflight、互斥锁、分布式锁或热点 key 保护。
- 不做延迟双删、订阅 binlog、MQ 或 Worker。
- 不做随机 TTL、缓存版本号或本地数据迁移。
- 不增加 Prometheus 等指标系统。
- 不缓存点赞状态、关注状态或作者作品列表。

这些能力不是错误，只是当前数据量、运行方式和学习目标还不需要它们。

## 3. 三个核心问题

### 3.1 缓存什么

```text
key:   myfeed:profile:{account_id}
type:  Redis STRING
value: 当前 Profile DTO 的 JSON
TTL:   固定 60 秒
```

只保存接口已经允许返回的字段：

```json
{
  "account": {
    "id": 12,
    "username": "alice",
    "avatar_url": "/static/avatar.png",
    "bio": "hello"
  },
  "stats": {
    "videos_count": 3,
    "likes_count": 28,
    "followers_count": 10,
    "followings_count": 5
  }
}
```

不要缓存完整 `Account` Model，也不要把 password hash、token、GORM 时间字段等内部字段写入缓存。

### 3.2 什么时候失效

- TTL 到期后自动失效。
- 关注/取关成功后删除关注者和被关注者的主页缓存。
- 点赞/取消点赞成功后删除视频作者的主页缓存。
- 发布视频成功后删除作者主页缓存。
- 评论不改变现有主页字段，不删除主页缓存。

### 3.3 Redis 挂了怎么办

- 读取失败：查询 MySQL 并正常返回。
- 回填失败：返回已经查到的 MySQL 结果。
- 主动删除失败：保留已经提交的 MySQL 业务结果，旧缓存依靠 60 秒 TTL 收敛。
- `cache.ErrDisabled` 表示项目启动时已经禁用 Redis，静默降级，不重复打印警告。

MySQL 始终是最终数据源，Redis 只是可丢弃的派生读模型。

## 4. 读取流程

建议把 `ProfileService.GetProfile` 调整为接收 `context.Context`：

```go
func (service *ProfileService) GetProfile(ctx context.Context, accountID uint) (*Profile, error)
```

完整流程：

```text
校验 account_id
  -> 尝试 GET myfeed:profile:{account_id}
     -> hit 且 JSON 正常：直接返回 Profile
     -> miss：继续查询 MySQL
     -> Redis 异常：记录 WARN，继续查询 MySQL
     -> JSON 损坏：尝试删除坏值，返回解码错误供 service 记录 WARN，继续查询 MySQL
  -> 完成现有 5 项 MySQL 查询
     -> 账号不存在：返回原有 404，不缓存空结果
     -> 查询失败：返回原有错误，不写缓存
  -> 尝试 SET JSON EX 60s
     -> 成功或缓存禁用：正常返回
     -> 失败：记录 WARN，仍正常返回
```

Redis `GET` 和 `SET` 分别使用 50ms 超时，与当前 token cache、video detail cache 保持一致。写链路中的每次 `DEL` 也使用 50ms 超时；删除双方主页时，即使其中一次失败也继续尝试另一次。缓存 hit 不续期，只有 MySQL 回源成功后才重新写入完整的 60 秒 TTL。

## 5. 主动失效范围

| 写操作 | 变化的主页字段 | 删除的缓存 |
|---|---|---|
| `follow` | 关注者 `followings_count`、博主 `followers_count` | follower + vlogger |
| `unfollow` | 关注者 `followings_count`、博主 `followers_count` | follower + vlogger |
| `like` | 视频作者 `likes_count` | author |
| `unlike` | 视频作者 `likes_count` | author |
| `video.Publish` | 作者 `videos_count` | author |
| 评论发布/删除 | 无 | 不删除 |

当前关注、取关、点赞和取消点赞都支持幂等。为了保持实现简单，只要业务方法最终成功，就可以尝试删除对应主页缓存；即使本次请求没有改变关系记录，多执行一次 `DEL` 的成本也可以接受，并且有机会清理上一次失败遗留的旧缓存。

主动删除必须发生在 MySQL 写入或事务成功之后。删除失败不能回滚已经完成的关注、点赞或发布操作。

当前还没有资料编辑、视频删除和视频状态修改接口。未来增加这些写操作时，再把对应主页缓存失效补到同一张表中，不提前设计不存在的链路。

## 6. 一致性边界

正常路径是“先写 MySQL，成功后删缓存”，大部分修改会立即在下一次主页查询中体现。

Cache Aside 仍存在一个可接受的并发窗口：

```text
请求 A cache miss，读到旧 MySQL 数据
请求 B 更新 MySQL，并删除缓存
请求 A 随后把旧数据重新写回缓存
```

本方案不通过锁或延迟双删消除这个窗口。重新写入的旧值最多存活约 60 秒，之后会自然过期。对于只影响展示的主页计数，这个边界与当前个人项目相匹配。

这里不要宣称“强一致”或“写后一定实时可见”。准确描述是：

```text
MySQL 最终正确；正常写路径主动失效；异常和并发情况下由 60 秒 TTL 有界收敛。
```

## 7. 代码结构

### 7.1 Profile Cache

新增：

```text
internal/profile/profile_cache.go
```

接口与视频详情缓存保持相似：

```go
type ProfileCache interface {
    GetProfile(ctx context.Context, accountID uint) (Profile, bool, error)
    SetProfile(ctx context.Context, accountID uint, profile Profile, ttl time.Duration) error
    DelProfile(ctx context.Context, accountID uint) error
}
```

Redis 实现负责：

- 使用已有 `cache.Client.ProfileKey(accountID)`。
- JSON 序列化和反序列化。
- 把 `redis.Nil` 转换为正常 miss。
- 发现坏 JSON 时尝试删除坏值，并把解码错误返回给 service；service 记录后回源 MySQL。
- Redis 未启用时返回 `cache.ErrDisabled`。

### 7.2 ProfileService

`ProfileService` 增加 `ProfileCache` 依赖，并在现有聚合逻辑前后加入读缓存和回填。

为了让“cache hit 不访问 repository”以及 Redis 故障降级可以做纯单元测试，可在 `profile` 包内把当前三个具体仓储依赖收窄为最小 reader 接口：

```text
AccountReader     -> FindAccountByID
VideoStatsReader  -> GetVideosCount + GetAuthorLikesCount
FollowStatsReader -> GetFollowersCount + GetFollowingsCount
```

现有三个 Repo 会自然满足接口，不新增一层“主页聚合 Repository”，也不移动现有 SQL。

### 7.3 写侧依赖

为避免 `follow`、`video` 反向导入 `profile` 造成包循环，各写业务包只定义自己需要的本地小接口：

```go
type ProfileCacheInvalidator interface {
    DelProfile(ctx context.Context, accountID uint) error
}
```

`profile.RedisProfileCache` 会自然满足这个接口。Router 创建一个实例，并同时注入：

- `ProfileService`
- `FollowService`
- `LikeService`
- `VideoService`

`FollowService.Follow/Unfollow` 和 `VideoService.Publish` 增加 `context.Context` 参数，由 handler 传入 `c.Request.Context()`；`LikeService.Like/Unlike` 已经有 context，不需要再改变 HTTP 层契约。

点赞链路在事务内已经读取视频。当前实现保留该视频的 `AuthorID`，待事务成功后再删除作者主页缓存，没有额外增加作者查询，也没有在事务提交前删除缓存。

这一处小接口和 context 传递是本轮唯一必要的结构调整，不引入事件总线或统一缓存管理器。

## 8. 日志方案

沿用当前最小日志策略：

- 不记录每次 cache hit、miss、set 成功或 delete 成功。
- `cache.ErrDisabled` 静默降级。
- 只记录 Redis 读取、回填、删除异常和坏 JSON。
- 不输出完整 Profile JSON，避免日志冗余和潜在信息泄露。

格式示例：

```text
level=WARN component=profile_cache operation=get account_id=12 err="..."
level=WARN component=profile_cache operation=set account_id=12 err="..."
level=WARN component=profile_cache operation=delete account_id=12 err="..."
```

本轮不为日志再引入 zap、slog 封装或 trace ID 系统。

## 9. 测试清单

建议保持在 7～8 组，不追求生产级组合爆炸：

1. Redis 未启用时，Profile Cache 返回 `cache.ErrDisabled`。
2. miniredis 验证 Profile JSON 的 set/get/delete 生命周期和 60 秒 TTL。
3. 坏 JSON 会被清理并触发 MySQL 回源。
4. cache hit 直接返回，并确认三个 reader 都没有被调用。
5. cache miss 完成五项聚合并回填；账号不存在时不回填空值。
6. Redis `GET/SET` 失败不影响 MySQL 正常结果。
7. follow/unfollow 成功后删除双方 key；删除失败时业务仍成功。
8. like/unlike 和 publish 成功后删除作者 key；删除失败时业务仍成功。

现有 MySQL Profile 聚合集成测试继续保留，用于验证统计 SQL；缓存分支主要通过 stub 和 miniredis 测试，不要求每次默认测试都连接本地 MySQL。

## 10. 实施顺序

1. 新增 `profile_cache.go` 和 Redis 生命周期测试。
2. 给 `ProfileService.GetProfile` 接入 Cache Aside，并补 hit、miss、故障降级测试。
3. 接入 follow/unfollow 双方缓存删除。
4. 接入 like/unlike 作者缓存删除。
5. 接入 video publish 作者缓存删除。
6. 在 Router 中统一组装一个 `RedisProfileCache`。
7. 执行 `gofmt`、`go test ./...`、`go vet ./...` 和 `git diff --check`。

分步实现可以让每一次改动都可编译、可测试，不需要一次重构所有缓存代码。

- [x] 缓存命中不续期。
- [x] Redis 不可用时接口仍可通过 MySQL 返回。
- [x] 不存在的账号不写空值缓存。
- [x] follow/unfollow 删除双方主页缓存。
- [x] like/unlike 删除视频作者主页缓存。
